## Codex 的额度是怎么算的：积分、5小时窗口、每周上限

先说一个前提：Codex 没有独立订阅，它包含在 ChatGPT 套餐里，和 ChatGPT Work 共用同一份额度。所以“Codex 额度”实际是“你这个 ChatGPT 档位在 Codex 上的用量”。

在这个前提下，三条规则决定了你实际能用多少：

**1. 按积分计费，不按条数。** 2026 年 4 月 2 日起，Codex 把计量方式换成了和 API token 价格挂钩的积分（credit）。一次轻量编辑和一次跨多文件的大重构，消耗可以差好几倍。官方给的不是固定数，是区间。

**2. 双时钟：5 小时窗口加每周上限。** 5 小时窗口是滚动制，从本轮第一次请求开始计时，连续 5 小时后这批额度释放回来；每种模型的额度独立计算，GPT-6 Sol 用光了不影响 GPT-6 Luna。窗口之上还有一层每周上限，触到之后就算新 5 小时窗口开始了，也得等每周重置。

**3. 本地和云端共享一个池子。** CLI、IDE 里的本地消息和云端任务从同一份额度里扣，云端任务通常单次消耗更大。

顺带提一段插曲：7 月中旬起，不少 Plus、Pro 和 Business 用户发现 5 小时窗口从用量页面里消失，只剩每周限制，官方没发公告，更新日志里也找不到这次变动。到 10 月初再核对时，滚动窗口的限制已经恢复。如果你按那阵子的手感估现在的额度，会偏乐观。

这张表最值得看的是模型之间的差距，而不是套餐之间的差距。同样在 Pro 20x 上，GPT-6 Luna 一个窗口能跑 7,000 到 56,000 条，GPT-6 Astra 只有 100 到 900 条，差了几十倍。把补全、格式化、写测试、改注释这类活交给 Luna，把 Astra 和 Sol 留给真正难的调试和架构决策，同样的额度能撑长得多的时间。

区间为什么这么宽？因为积分按 token 走。官方给 GPT-5.6 系列的参考值是平均每条消息 5–30 积分，短编辑贴着下限，长上下文的 agent 任务会往上限走。

另外提醒一句：GPT-5.5 将在 10 月 14 日从 ChatGPT 和 Codex 全套餐退役，API 不受影响。配置文件里还钉着 gpt-5.5 的记得提前换，不然 CLI 会回退到默认模型，而那个默认模型未必是你想花的钱。

## 每周上限、重置时间和剩余额度在哪看

每周上限没有官方公开的固定数值。有第三方根据社区反馈整理的估算是一周之内连续跑满 10–15 个 5 小时窗口就可能触发，仅供参考，按这个口径，普通工作日的开发强度基本碰不到，全天候挂 agent 的重度用户才需要留意。

重置和查询相关的几件事：

- **重置时间以官方用量面板为准。** 面板会显示当前剩余额度和重置时间，没有别的“重置查询工具”。
- 终端里也能查：`/status` 看当前模型和用量，`/usage` 打开账户用量（支持 daily、weekly、cumulative），`/statusline` 可以把剩余额度固定在界面底栏。
- 不同模型的额度分开重置。某个模型用完时它自己暂时不可用，其他模型照常，页面会显示恢复时间。
- 攒下来的重置（earned reset）在 `/usage` 里兑换，但有 **30 天有效期，从发放当天开始算**，不是从你使用那天开始算。6 月那波推荐活动发的重置，现在都已过期。
- 客服不能手动重置额度，官方文档写得明白。除非用量看起来算错了，否则别指望工单。

## 额度用完了怎么办：四条路和各自的成本

任务跑到一半触顶，agent 可以把当前这一轮做完（受公平使用约束），之后的选项按顺序考虑：

1. **等重置。** 面板上的时间到了自动恢复，成本为零。
2. **买积分。** Plus 和 Pro 用户可以买额外积分接着用，不用升级套餐，积分单价随档位有差异。积分按 token 计费，Standard 速度的费率如下：

| 模型 | 输入 | 缓存输入 | 输出 |
| --- | --- | --- | --- |
| GPT-6 Astra | 250 | 25 | 1,250 |
| GPT-6 Sol | 50 | 5 | 250 |
| GPT-6 Luna | 2.5 | 0.25 | 12.5 |
| GPT-5.6 Sol | 100 | 10 | 500 |
| GPT-5.6 Luna | 5 | 0.5 | 30 |

（单位：积分 / 百万 token）

两个对成本影响最大的数字：输出 token 的积分费率大约是输入的 5–6 倍，长输出、大段解释代码的习惯会明显加速烧积分；缓存命中的输入只按十分之一计费，固定系统提示词、用 `--resume` 续会话而不是每次开新会话，能把长会话的输入成本压下去一大截。

还有两个开关会让额度消耗得更快：Fast mode 在 GPT-6 系列上按 Standard 费率的 2.5 倍扣；图片生成平均按 3–5 倍消耗。非紧急任务把 Fast mode 关掉，是最省事的一笔账。

3. **挂 API Key。** 任何档位都可以在 Codex 里绑 API Key 跑额外会话，按标准 API 费率计费，不占订阅额度。CI/CD 这类无人值守任务用它反而更好预算。
4. **工作区积分。** Business、Edu、Enterprise 灵活计费的团队可以买工作区积分。

一个实用的判断：有第三方测算过，如果你每周都得靠买积分续命，说明档位低了，升级的钱通常比持续买积分便宜。OpenAI 在费率说明里给的估算也差不多——一个典型开发者每月的用量大约值 $100–200，取决于模型选择、实例数量和自动化程度。

## 额度不够用时的省额度清单

- **简单任务切到 Luna。** 同一档位里 Luna 的可用条数比 Sol、Astra 高出一个数量级以上，补全、格式化、生成注释、改变量名没必要动用旗舰模型。
- **用桌面 App 客户端。** 有第三方整理的资料和截图显示，Codex App 的可用额度是 CLI 和网页的两倍，网页或 CLI 报限额时切到 App 往往还能继续干活。
- **干完一个模块就开新会话。** 会话越长，每次请求背着的上下文越多，积分烧得越快。
- AGENTS.md 放在子目录而不是仓库根目录，控制每次注入的上下文体积。
- 关掉用不上的 MCP 服务器，每个活跃工具都会给每条消息多包一层上下文。

## "Selected model is at capacity" 不是额度用完

完整报错是"Selected model is at capacity. Please try a different model."，意思是 OpenAI 服务端这个模型的算力满了，和你的配额无关。官方仓库有两个仍然打开的 issue 记录了最近两波大面积出现的情况：一次在 8 月底，Pro 用户在额度充足时反复触发；一次在 9 月初 GPT-6 Astra 上线之后，CLI、IDE 和网页端都有报告。

处理办法就两个：`/model` 换个模型，或者过一会儿重试。别因为这个报错去买积分，买了也解决不了容量问题。
